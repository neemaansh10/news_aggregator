===============================================================================
                     NEWS AGGREGATOR - SIMPLE ENGLISH GUIDE
===============================================================================

This document explains the complete step-by-step lifecycle of the News Aggregator 
project in simple, easy-to-understand English.

-------------------------------------------------------------------------------
1. HOW DATA IS FETCHED FROM WEBSITES (Ingestion & Parallel Polling)
-------------------------------------------------------------------------------
- The system continuously fetches news articles from thousands of RSS/Atom feeds 
  (such as BBC, Reuters, Guardian, NPR).

- **Fetching at the Same Time (Concurrency):**
  Instead of fetching websites one by one, async background workers fetch multiple 
  feeds simultaneously using non-blocking network calls.

- **Smart Bandwidth Saver (Conditional GET):**
  When fetching a website, our system sends `ETag` and `Last-Modified` headers. 
  If the website has NO new articles, it replies with an empty response (`HTTP 304`). 
  This saves over 95% of server bandwidth.

- **Adaptive Polling Cadence:**
  If a news feed posts new articles frequently, we poll it more often. If a feed 
  is quiet, we automatically slow down its polling frequency.

- **Circuit Breaker (Failure Protection):**
  If a website goes down or returns errors 5 times in a row, the system pauses 
  polling it temporarily so we do not overload their servers or ours.


-------------------------------------------------------------------------------
2. HOW DATA IS NORMALIZED (Bringing All Articles into the Same Format)
-------------------------------------------------------------------------------
Different news websites publish content in messy formats (HTML tags, tracking links, 
advertisements, different encodings). The Normalizer cleans every raw article:

1. **URL Cleaning (Canonicalisation):**
   - Converts `HTTP` to `HTTPS`.
   - Strips tracking parameters like `?utm_source=twitter` or `?fbclid=xyz`.
   - Example: `https://ft.com/news?utm_source=rss` becomes `https://ft.com/news`.

2. **Text Cleaning:**
   - Strips HTML tags, ads, and extra whitespace.
   - Normalizes text accents and special Unicode characters.

3. **Entity Extraction:**
   - Extracts important named entities (People, Places, Organizations) such as 
     `"Federal Reserve"`, `"Japan"`, `"BBC"`.

4. **Standard Schema (`NormalisedArticle`):**
   Now, every article from every website is stored in the exact same format:
   - `title`: Clean headline
   - `body`: Clean text
   - `url_hash`: Unique hash of clean URL
   - `entities`: Set of key proper nouns
   - `published_at`: Standardized UTC timestamp


-------------------------------------------------------------------------------
3. HOW DUPLICACY IS CHECKED (5-Layer Cascade)
-------------------------------------------------------------------------------
When a new article arrives, it passes through 5 fast layers (cheapest first):

- **Layer 1a: Exact URL Check**
  If the clean URL hash already exists in our database, it is rejected immediately 
  as an exact duplicate (or updated if text changed).

- **Layer 1b: Exact Content Check (SHA-256)**
  If different URLs have the exact same body text (SHA-256 hash match), it is 
  marked as duplicate.

- **Layer 2a: Wire Copy / Rewritten Headline Check (SimHash + LSH)**
  Many newspapers copy wire stories from Reuters/AP and only change the headline.
  - SimHash turns the body text into a 64-bit fingerprint.
  - LSH splits the 64 bits into 8 bands.
  - By mathematical guarantee (Pigeonhole Principle), if two articles are near-duplicates 
    (Hamming Distance <= 7), they MUST match on at least 1 band.
  - This allows sub-second instant duplicate detection in database indexes.

- **Layer 3: Story Clustering (Is it the Same Story?)**
  Articles covering the same real-world event are grouped into a single **STORY**.
  - **TF-IDF Text Match:** Converts article text into term vectors.
  - **Entity Match:** Calculates overlap of extracted named entities.
  - **Composite Score:** `0.70 * Text_Similarity + 0.30 * Entity_Overlap`.
  - If Composite Score >= 0.30, the article joins an existing Story. Otherwise, 
    a new Story is created.

- **Layer 2b: In-Cluster MinHash Check**
  Once an article is inside a Story, MinHash checks body 3-shingles against other 
  articles in the same story. If similarity > 0.45, it is marked as a syndicated copy.


-------------------------------------------------------------------------------
4. HOW EVERYTHING RUNS AT THE SAME TIME (System Concurrency & Kafka Bus)
-------------------------------------------------------------------------------
- The system is built with decoupled microservice stages:
  `Ingestion` -> `Normalisation` -> `Clustering` -> `Ranking` -> `API`

- **Kafka Event Bus (or In-Memory Bus):**
  Messages pass between stages as streaming events. If one stage slows down, 
  events queue up safely without losing data.

- **Sharding by Blocking Key:**
  Articles are partitioned by language and topic key. Articles about the same 
  event always route to the same worker thread, preventing race conditions 
  without needing global database locks.


-------------------------------------------------------------------------------
5. HOW THE USER FEED IS UPDATED AND SERVED
-------------------------------------------------------------------------------
- **Story Scoring Formula:**
  Every Story is given a rank score based on 3 factors:
  `Score = Source Authority * Syndication Multiplier * Recency Decay`

  1. **Source Authority:** Stories reported by multiple independent credible 
     sources receive higher points.
  2. **Syndication Multiplier:** If 10 outlets publish identical wire copy, 
     they do NOT get 10x score. They are heavily discounted so fake/spam copies 
     cannot manipulate ranking.
  3. **Recency Decay:** Scores naturally decrease over time so new breaking news 
     stays at the top.

- **Background Ranker:**
  A background job continuously recalculates story scores every few seconds.

- **FastAPI Feed Serving (`GET /v1/feed`):**
  Users request news from a fast API. The feed uses **Cursor-Based Pagination**, 
  meaning as the user scrolls or refreshes, already seen stories are tracked 
  so the user never sees duplicate news!
